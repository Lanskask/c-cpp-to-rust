## 0. Scope and posture

- One Part (`parts.tsv`): `src/tinyjson` (`src/tinyjson.h`, header-only) → `rust/src/lib.rs`. `test/`, `samples/`
  and the vendored `test/catch.hpp` are not Parts.
- C++ route (judge.md §1, decision 5): the original tests cannot link to a Rust crate, so there is **no C ABI** in
  either Stage. Stage 1 exports a Rust API that keeps the C++ names and structure (§5); the Judge reaches it through
  the adapter `rust/tests/adapter/mod.rs`.
- Stage 1 (Faithful port): same structure, same names, `unsafe` allowed. `class json` keeps its hand-made tagged
  union (`void* _value` + `json_t _type`, CPP7); `class parser` keeps its static functions over a `char32_t` stream
  (CPP26, CPP29). You are translating, not improving.
- Stage 2 (Idiomatic pass): the API in §6, zero `unsafe`, acceptance rules in §10. Same behaviour, not same API. The
  user's rule applies: Stage 2 keeps the C++ functionality as close as possible, and every divergence is a §8 row.
- Engine for Stage 1: LLM (c2rust does not translate C++).
- Reference behaviour: the header does not build with Apple clang/libc++ (D16), so the original side of every Judge
  piece is built with GCC 16 + libstdc++ (§10). Where that build has UB (D3), the upstream tests' expected values
  decide.
- Run `cargo check` in the inner loop; `gate.py` alone decides acceptance.

## 7. Error model

- C++ signals every failure by an exception (CPP21). Both Stages return `Result<T, Error>` with `Error { kind, what }`.
  `kind` keeps the C++ class: `RuntimeError` (every `throw` in the header, including the rethrows of `U32ToU8` /
  `U8ToU32`), `InvalidArgument` and `OutOfRange` (from `std::stoll`/`std::stod`, which the header does not catch,
  D8). `what` is the exact `what()` text (Q14).
- **precondition-guards** (kept, same message, both Stages): `CHECK_TYPE_MISMATCH` in every getter and mutator
  (`tinyjson.h:366-422`), `size()` on a non-container (`440`), missing key (`449-452`), index out of range (`463-466`),
  the conversion operators (`507`, `518`, `529`, `540`), and every parser error (`648-1065`).
- **unreachable guards**: the `default:` arms that handle `json_t::invalid` (`253-254`, `287-288`, `569-570`). No
  constructor or parser path builds an `invalid` value, so they cannot run (reasoned). Stage 1 keeps them as
  `unreachable!()` with an invariant comment (CPP14); Stage 2 has no `Invalid` payload.
- **allocation-guards**: none in the source; `new` throws `std::bad_alloc` (D14).
- Partial state after an error (E4): an exception leaves `*this` unchanged in every member function (each throws
  before it writes, reasoned). A parser function that throws leaves the caller's stream at the position where it
  stopped (Q13); `parser::parse` owns its stream, so only the error is observable there.

## 10. Judge and acceptance

Proposed; ticket 02 builds it.

- Feature matrix: `""` only (§3). Gate: `make pilot-tinyjson STAGE=<n>`.
- Reference build: Homebrew GCC 16 (`g++-16 -std=c++17 -include locale`) + libstdc++ on macOS arm64. Apple clang
  cannot build the header (D16). The test file is built from a copy with two patches: the include `..\src\tinyjson.h`
  (`tests:4`, a Windows path) and `9876543210` → `9876543210LL` (`tests:70`, D7). Measured on that build: 22 test
  cases, 17 pass, 5 fail, all through D3.
- Stage 1 and Stage 2 (C++ route, judge.md §1): translated tests `rust/tests/tinyjsonTests.rs` with the upstream
  inputs and expected values (all 22 cases, the 5 D3 cases included), and the Differential harness: a C++ driver
  built against the Reference vs `rust/examples/dump.rs`. The driver parses one input file and prints, for every
  node: `type()`, `type_name()`, every getter's result or error kind + text, `size()`, `to_string()`; plus the
  equality matrix over the defined pairs (Q1, D2, not D1), and copy/assign round trips. Errors print as
  `<kind> <what>`.
- Corpus classes to handle (judge.md §3, §5a): inputs with `\u` (D3), invalid UTF-8 (D5), deep nesting (D11),
  locale-dependent numbers (D8, D9: run both sides in the C locale). Allocation failure: no hooks exist (D14), not
  testable. Input without a NUL: the adapter passes the slice as is (`parse` stops at the first NUL, Q10).
- Stage 2 adds: clippy `-D warnings`, rustfmt, zero `unsafe`, no `unwrap()`/`expect()` on input-driven paths (others
  need an invariant comment) (decision 10).
- Extra tests (not upstream, both Stages): D1 pairs give `false`; Q1 container vs null gives `true`; D2 measured
  values; Q4, Q5 serialisation; Q9 separators.
